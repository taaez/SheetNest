# 웹 화면 v2 (실무용)

`web/`의 첫 화면을 그대로 두고, 팀 피드백을 반영해 복제한 화면이다. 계산 코드(`web/bridge.py`, `nesting/`, `algorithms/`)는
두 화면이 같이 쓰므로 수치는 똑같고, 화면 구성과 문구만 다르다.

| 주소 | 폴더 | 성격 |
|---|---|---|
| https://taaez.github.io/SheetNest/ | `web/` | 알고리즘 비교 중심 (첫 화면, 그대로 유지) |
| https://taaez.github.io/SheetNest/v2/ | `web_v2/` | 실무용: 필요한 원판 길이를 먼저 보여 줌 |

## 첫 화면과 다른 점

| 피드백 | v2에서 바꾼 것 |
|---|---|
| 실무자가 볼 결론(원단 길이) | 결과 맨 위에 결론 카드: 가장 짧게 나온 방법과 필요한 원판 길이, 이론상 최소와의 차이, 버려지는 비율, 방법별 길이(짧은 순)와 차이 |
| 상황에 따라 우선순위 고르기 | "무엇을 우선할까요?": 자재 절약 우선(제한 없음), 시간 제한 안에서 자재 절약(기본, 1초/10초/1분/10분 중 1분), 계산 속도 우선. 시간 선택지는 실험 3의 제한 시간 T와 같다 |
| 실무에서는 세 방법을 다 돌릴 수 없다 | 도면을 고르면 계산 전에 방법별 예상 시간과 추천 방법을 보여 주고, "추천 방법으로 계산"은 그 방법 하나만 돌린다. 준비된 도면은 실험 3에서 잰 시간표(`timing.js`), 올린 도면은 조각 수와 볼록 조각 수의 합으로 어림한다 |
| 추천 규칙 | 시간 안에 끝날 것으로 예상되는 방법 중 NFP, 삼각법, 래스터 순(길이는 예측식 없이 실측 빈도에 따른 순서). 계산 속도 우선은 예상 시간이 가장 짧은 방법 |
| 시간 제한 안의 최소 길이, 넘으면 시간 초과 | "고른 방법 모두 계산해 비교"는 방법마다 작업자를 따로 띄워 동시에 돌리고, 실제 계산을 시작한 때부터 제한 시간을 잰다. 넘긴 방법은 그 작업자만 끝내고 "시간 초과"로 표시한 뒤 끝난 방법 중 가장 짧은 배치를 고른다 |
| 추천과 실제가 다를 때 그대로 보여 주기 | 모두 계산한 뒤 추천과 다르면 "추천은 NFP였지만, 이번에는 래스터가 NFP보다 1.1% 짧았습니다"처럼 알려 준다. 추천한 방법이 예상과 달리 시간 초과가 되어도 알려 준다 |
| 속도보다 길이 강조 | 결론 카드, 비교표, 배치 그림 모두 길이가 짧은 순으로 놓고 가장 짧은 방법에 "가장 짧음" 표시. 내려받기도 가장 짧은 배치. 계산 시간은 비교표에만 남김 |
| 실제 길이로 보기 | "실제 원판 폭" 칸. 적으면 도면 단위를 실제 길이(m, cm)로 바꾸고, 내려받는 SVG와 DXF도 실제 크기(mm)로 만든다 |
| 검증 빼기 | 비교표의 검증 칸을 없애고 결론 카드에 한 줄로 남김. 실패한 방법만 표에 빨간 표시 |
| 계산량 | 비교표에서 빼서 "계산량 자세히"(접힘)로 옮김 |
| 내 도면 올리기 | 실무에 필요한 기능이라 유지. 접힌 채로 두고 안내 문구를 쉽게 고침 |
| 멘트 | 제목, 단계 번호(1 도면 고르기, 2 계산하기, 3 결과), 방법별 한 줄 설명, 표 머리글을 쉬운 말로 |
| 큰 입력 | 계산 중 경과 시간 표시, 멈추기 단추, 오래 걸리는 도면(gardeyn2~9)과 NFP가 오래 걸리는 gardeyn1에 표시 |
| 올린 파일 | 도면 목록 맨 위에 "올린 파일: 이름"으로 보이고, 준비된 도면을 골랐다가 다시 돌아올 수 있음 |
| 실제 크기 DXF | 단위(mm)를 파일에 적어 두어, 내려받은 DXF를 다시 올리면 단위와 폭을 자동으로 알아봄 |

## 내 PC에서 열기

```bash
python tools/build_web.py --serve
```

http://localhost:8000/v2/ 를 연다. 첫 화면은 http://localhost:8000/ 에 그대로 있다.

## 고칠 때

- 이 폴더만 고친다. `web/`은 건드리지 않는다(`tests/test_web_bridge.py`가 두 화면이 각자 폴더 그대로 배포되는지 검사한다).
- 삼각법과 래스터의 `rows`(원판 폭 ÷ 값 = 간격) 입력칸은 `web/bridge.py`의 `PARAMS`에서 오므로 두 화면에 함께 나온다.
- 우선순위는 `app.js`의 `priority()`, 계산 전 추천은 `expectedSeconds()`, `recommend()`, `renderRecommend()`, 계산은 `startRun()`, `runner()`, `launch()`, `onTimeout()`. 화면 쪽 작업자는 도면 읽기만 하고, 방법마다 계산 작업자를 하나씩 띄운다(처음 계산할 때 몇 초 더 걸리고, 그다음부터는 다시 쓴다).
- 예상 시간표 `timing.js`는 실험 3 결과(`results/exp3_instances.csv`)로 만든다. 알고리즘 속도가 바뀌면 실험 3을 다시 돌리고 표를 새로 만들어야 한다. 표의 값은 PC 시간이고 브라우저는 `factor`(1.7)배로 본다. 사용자 컴퓨터가 측정한 컴퓨터보다 느리면 예상보다 오래 걸린다.
- 방법 설명 문장은 `app.js`의 `METHOD_DESC`, 오래 걸리는 도면 목록은 `SLOW`(모든 방법)와 `SLOW_METHOD`(특정 방법만)에 있다.
- 멈추기는 Python 계산을 중간에 끊을 수 없어서 작업자(Web Worker)를 끝내고 새로 띄운 뒤 같은 도면을 다시 불러온다. 몇 초 걸린다.
